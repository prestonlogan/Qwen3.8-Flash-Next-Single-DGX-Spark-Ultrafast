# Long context, v1.1.0 default (2026-11-24)

Three tests on one DGX Spark: decode speed with the context already filled, RULER at 32K to 128K, and an agent task
far larger than the context window that survives only through its own summaries.

**What ran.** The v1.1.0 default (`PROFILE=fast`, `TUNING=v1.1`, `VISION=1`) on the release-candidate image
`20261123-t94-rc-clean`, with the released draft head (SHA-256 `964a0756…` and `b2db323c…`, the same files
`tools/download.sh` pins). Requests went through a local gateway in front of the server. The scripts here default to
the recipe's own port (`http://127.0.0.1:8888`, model `local-ai`, no key); set `URL` or `BASE`, `MODEL` and `API_KEY`
to point them elsewhere.

## Decode speed at depth: `depth/`

tool-eval-bench perf mode: a 2,048-token prompt and 512 output tokens on top of a context already filled to each depth,
temperature 0, 2 runs each. Full report: [depth/report.md](depth/report.md). Rerun: `depth/run_depth.sh`.

| Context already filled | Decode tok/s | Time to first token |
|---:|---:|---:|
| 0 | 124.2 | 1.0 s |
| 32K | 104.2 | 11.1 s |
| 64K | 101.4 | 22.5 s |
| 100K | 94.1 | 35.2 s |
| 150K | 86.0 | 53.5 s |
| 200K | 72.1 | 74.7 s |
| 250K | 69.4 | 86.6 s |

Decode stays near 70 tok/s at 250K. The cost at depth is prefill: the depth here is uncached, so an uncached 250K
prompt waits about 87 s for its first token. Prompts already in the prefix cache skip that.

## RULER: `ruler/`

[NVIDIA/RULER](https://github.com/NVIDIA/RULER)'s 13 synthetic tasks, prompts generated by RULER's own `prepare.py`
with this model's tokenizer. Chat API, thinking off, temperature 0, scored as RULER does (`string_match_all`;
`string_match_part` for QA). 5 samples per task at 32K, 3 at 64K and 128K.

| Task | 32K | 64K | 128K |
|---|---:|---:|---:|
| 8 retrieval tasks (single, multi-key, multi-value, multi-query) | 100 | 100 | 100 |
| Variable tracking (vt) | 92 | 100 | 87 |
| Common words (cwe), 1,024 output tokens | 80 | 67 | 100 |
| Frequent words (fwe) | 100 | 89 | 100 |
| QA 1 (SQuAD) | 100 | 100 | 100 |
| QA 2 (HotpotQA) | 80 | 67 | 67 |
| **Average, 13 tasks** | **96.3** | **94.0** | **96.4** |

- **cwe ran with 1,024 output tokens; every other task with 128.** At 128 the model starts counting the words step
  by step and runs out of room before it lists them, which scores 18 / 10 / 70 (those rows are in `results.jsonl`;
  `ruler_report.py` uses `results_cwe1024.jsonl` for cwe). The remaining cwe misses are runs still counting at 1,024.
- **The misses.** vt: each miss traced 4 of the 5 variables. QA 2: one 32K miss answered "Greenwich Village" where
  the reference is "Greenwich Village, New York City"; the 64K and 128K misses are the same question answered wrong.
- **Small samples.** With 3 to 5 samples a task score moves in steps of 20 to 33 points, so read the per-length
  averages, not single tasks. 192K was not run.

Rerun: clone RULER and install its requirements, then `TOKENIZER=<checkpoint dir> ruler/gen_ruler.sh`, then from
`ruler/`: `python3 ruler_run.py 32768 5`, `python3 ruler_run.py 65536,131072 3`, the cwe rows with
`TASKS=cwe python3 ruler_run.py 32768 5 1024 results_cwe1024.jsonl` (and `65536,131072 3`), and
`python3 ruler_report.py`. A 128K sample takes about 50 s, almost all of it prefill.

## Compaction agent test: `compaction/`

An agent task about 6 times larger than the context window. The agent reads 20 RFCs (194 pages of 20,000 characters,
roughly 900K tokens) one page at a time through a `read_doc` tool. Twelve editor's notes planted in them are the
whole specification of a small HTTP request linter, `httplint.py`; the agent has to find all 12, then write the tool
and its tests in a sandbox (`python:3.12-slim`, no network) and call `finish`. When a turn passes 150K tokens, the
conversation is replaced by a summary the agent writes itself; files in its workspace persist. Thinking on, the
model's default sampling (temperature 1.0). Stop rules: the same call 4 times in a row, 45 minutes without progress,
3 engine errors in a row, 5 hours, 1,500 turns. None fired.

**Result: 24 of 25 hidden checks, 11 of 12 notes fully met, 6 compactions.**

| | |
|---|---|
| Outcome | called `finish` on its own after 168 turns, 41 minutes |
| Compactions | 6, at 151K–158K tokens; summaries 3.8K–12K tokens |
| Pages read | 178 of 194 |
| Hidden checker (`checker.py`) | 24 of 25 cases; notes 1–9, 11, 12 fully met; note 10 failed |

- **The failure was an invented requirement, not a forgotten one.** Around compactions 4 and 5 the agent wrote a
  "note 11" into its `NOTES.md` that exists nowhere in the documents, presented as a verbatim quote from RFC 9293: a
  header line with no colon gets a new code, H010. It built that rule into the tool ahead of the real note 10, so a
  folded header line reported H010 instead of H009. The real note 11 (where the header section ends, sorted output)
  was still implemented and passed. The agent's finish message said it had found all 12 notes.
- **What carried it.** Besides its summaries, the agent kept `NOTES.md` in the workspace and went back to its files
  right after three of the six compactions. The last note, at 80% of the last RFC, was found and implemented.

Files: `run1.log` and `run1/events.jsonl` (every turn and compaction), `run1/summary-1.md` to `summary-6.md` (the
agent's summaries), `run1/workspace/` (what it built: `httplint.py`, `test_httplint.py`, `NOTES.md`, `REVIEW.md`),
`run1-checker.txt` (the checker's output). `reference_httplint.py` is the reference solution used only to validate the
checker (25 of 25); the agent never saw it.

Rerun from `compaction/`: download the 20 RFCs as `rfc/rfcNNNN.txt` from `https://www.rfc-editor.org/rfc/rfcNNNN.txt`
(the list is in `build_corpus.py`), then `python3 build_corpus.py`, `python3 agent.py run2`, and
`python3 checker.py run2/workspace`. Docker with the `python:3.12-slim` image is needed for the sandbox and the checker.
